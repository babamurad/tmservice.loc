### Этап 2A. Верификация телефона (OTP) — до публичного запуска

> **Открытый вопрос — SMS-шлюз для Туркменистана — кабинетная часть спайка
> проведена, финальный шаг (живой тест) — ещё нет.** Полный разбор:
> [`sms-gateway-spike.md`](./sms-gateway-spike.md). Коротко: у Vonage есть
> отдельная страница правил именно для `+993` — P2P запрещён, alphanumeric
> sender ID подменяется на случайный номер, двусторонний SMS не
> поддерживается; крупные агрегаторы (Twilio, Infobip и др.) формально
> числят страну «поддерживаемой», но это низкая планка (прайс-лист есть у
> 200+ стран). Ни одного публичного подтверждения реальной доставки OTP на
> живой `+993`-номер не нашлось — вопрос всё ещё открыт, не «наверное
> сработает». `LogSmsGateway` (код в лог) остаётся единственной реализацией,
> пока кто-то не проведёт финальный шаг — отправку через Vonage/Twilio
> триал на реальный номер (инструкция в спайк-документе, это должен сделать
> человек — у меня нет живого `+993`-номера и я не могу зарегистрироваться
> в провайдере).

### Этап 2B. Rate limiting — до публичного запуска

**Проблема**: `GET /api/masters/{id}` отдаёт телефон публично (by design),
но без лимита базу легко спарсить. `login`/`send-otp` без лимитов открыты
для брутфорса и SMS-флуда (SMS — это ещё и деньги).

- [x] Шаг 2B.1: Именованные лимитеры — сделано в `app/Providers/AppServiceProvider.php@boot()` (не в `bootstrap/app.php` — там для этого нет подходящего хука в Laravel 13, `RateLimiter::for` регистрируется в провайдере):
  ```php
  RateLimiter::for('public-read', fn (Request $r) => Limit::perMinute(60)->by($r->ip()));
  RateLimiter::for('auth',        fn (Request $r) => Limit::perMinute(5)->by($r->ip()));
  RateLimiter::for('otp',         fn (Request $r) => Limit::perMinutes(60, 5)->by($r->input('phone')));
  ```
- [x] Шаг 2B.2: `throttle:public-read` на `GET /api/masters`, `GET /api/masters/{id}` (`routes/api.php`).
- [x] Шаг 2B.3: `throttle:auth` на `login`/`register`, `throttle:otp` на `send-otp`/`verify-otp` — подключено вместе с Этапом 2A.

Покрыто тестами: `tests/Feature/RateLimitTest.php` — 6-я подряд неудачная
попытка логина за минуту → `429` с `Retry-After`; 61-й запрос `GET /api/masters`
за минуту → `429`. Полный набор тестов (`php artisan test`) — зелёный.

**Критерии приёмки**: превышение лимита → `429` с `Retry-After`. Массовый перебор `masters/{id}` упирается в лимит.

## Этап 7. Управление портфолио (удаление/лимит)

- [x] Шаг 7.1: `DELETE /api/profile/portfolio/{id}` (`auth:sanctum`,
  `ProfileController@deletePortfolio`) — проверка владения (чужое фото →
  `403`, несуществующее → `404`), удаляет и файл из `storage`, и запись в

- [x] Шаг 7.2: Лимит 10 фото на профиль (`ProfileController::MAX_PORTFOLIO_IMAGES`)
  — проверяется в начале `portfolio()`, до валидации файла, отдаёт `422`
  с понятным сообщением.

**Побочная находка — живой баг в загрузке фото.** Пока писал тест на
«загрузка при пустом лимите» (до сих пор ни один тест не доходил до
реального вызова `Image::read()`), обнаружил, что `ProfileController@portfolio`
вообще не мог загрузить фото: `intervention/image-laravel` резолвится в
v4/v5, где фасад `Image` не имеет метода `read()` — только `decode()`/
`decodePath()`/... — и у `ImageInterface` нет `toWebp()`, только
`encode(EncoderInterface)`. Заменил `Image::read($path)->resize(...)->toWebp(...)`
на `Image::decodePath($path)->resize(...)->encode(new WebpEncoder(quality: 80))->toString()`.
Без этого исправления любая реальная загрузка фото в проде падала бы с
`500` — это не было следствием моих изменений, баг был в коде до C3,
просто до сих пор ничем не тестировался.

Покрыто тестами: `tests/Feature/PortfolioManagementTest.php` — удаление
своего фото, запрет на чужое, `404` на несуществующее, отказ загрузки на
лимите, успешная загрузка чуть ниже лимита (это и есть тест, который
поймал баг с `Image::read()`). Полный набор тестов (`php artisan test`) —
зелёный (55/55).

**Критерии приёмки**: мастер удаляет своё фото, чужое — не может ✅. Превышение лимита — понятная ошибка ✅.

## Этап 8. Отзывы и рейтинги (рекомендуется в MVP)

**Проблема**: сейчас клиент выбирает мастера по имени + точке
«свободен/занят» — это про занятость, а не про качество. Без рейтинга нет
сигнала, хорош мастер или нет, а доверие в этой нише — весь продукт.

> **Открытый вопрос — кто может оставлять отзыв — решено (вариант а).**
> Любой верифицированный `client` может оставить один отзыв мастеру, отзыв
> уходит на модерацию. Вариант «отложить до заявок в приложении» не
> выбирался — в приложении заявок как не было, так и нет, ждать их
> появления означало бы не делать отзывы вообще.

- [x] Шаг 8.1: Модель `Review` — `client_id`, `master_profile_id`, `rating`
  (1–5, `unsignedTinyInteger`), `comment` (nullable), `moderation_status`
  (default `pending`, как у `MasterProfile`). Уникальный индекс
  `(client_id, master_profile_id)` — БД сама не даст оставить второй отзыв,
  плюс явная проверка в контроллере ради человекочитаемой ошибки вместо
  `500` от нарушения constraint.
- [x] Шаг 8.2: `master_profiles.avg_rating` (decimal 3,2), `reviews_count`
  (unsigned int) — не через observer/событие, а явный метод
  `MasterProfile::recalculateRating()`, вызываемый из `Review::approve()`/
  `reject()`. Соответствует смыслу денормализации (агрегат должен считаться
  только по `approved`-отзывам) точнее, чем сработавшее бы на любое
  сохранение событие модели.
- [x] Шаг 8.3: `POST /api/masters/{id}/reviews` (`ReviewController@store`,
  `auth:sanctum`) — `403`, если не `client` или телефон не подтверждён;
  `422` на повторный отзыв; создаёт со статусом `pending`. `GET
  /api/masters/{id}/reviews` (`ReviewController@index`, публичный,
  `throttle:public-read`) — только `approved`, с пагинацией, **явно не
  отдаёт `client_id`** (приватность автора отзыва — `select()` со списком
  полей, а не скрытие через `$hidden` на модели, поле остаётся видимым в
  админке). `avg_rating`/`reviews_count` теперь настоящие колонки —
  автоматически попадают в `GET /api/masters(/{id})` без доп. кода.
- [x] Шаг 8.4: `MasterController@index`: `->orderByDesc('is_free')->orderByDesc('avg_rating')`.
- [x] Шаг 8.5: `Admin\ReviewModerationController` (`/api/admin/reviews`,
  `?moderation_status=`, `approve`/`reject`) — тот же паттерн, что
  `MasterModerationController` в Этапе 5. `approve()`/`reject()` дёргают
  `recalculateRating()` на связанном профиле, так что рейтинг в публичном
  API обновляется сразу.

**Побочная находка, напрямую мешавшая фиче.** У формы «оставить отзыв» в
мобильном приложении нет способа узнать роль/верификацию текущего
пользователя после перезапуска приложения: `useAuth.js@restoreToken`
доставал токен из `SecureStore`, но ставил `user = { token }` — с пометкой
`// TODO: fetch user profile to validate token`. Без роли/`phone_verified_at`
форма отзыва не смогла бы понять, кому её показывать, у любого клиента
после перезапуска приложения (не только что залогинившегося) форма была бы
скрыта. Добавил `GET /api/me` (`AuthController@me`, `auth:sanctum` —
отдаёт `$request->user()`) и переписал `restoreToken()` на реальный запрос
профиля вместо заглушки.

Покрыто тестами: `tests/Feature/ReviewTest.php` (создание отзыва,
`pending` не влияет на `avg_rating`, роль/верификация блокируют, дубликат
запрещён, рейтинг вне 1–5 отклоняется, публичный список только `approved`
и без `client_id`, сортировка и агрегаты в `GET /api/masters`),
`tests/Feature/AdminReviewModerationTest.php` (список по статусу,
`approve`/`reject` пересчитывают рейтинг, не-admin не может модерировать),
`tests/Feature/AuthMeTest.php` (`/api/me` для авторизованного/гостя).
Полный набор тестов (`php artisan test`) — зелёный (69/69).

**Критерии приёмки**: клиент — один отзыв на мастера, 1–5 звёзд ✅. Рейтинг
и число отзывов видны в списке/карточке ✅. Неодобренные отзывы не
показываются публично ✅.
