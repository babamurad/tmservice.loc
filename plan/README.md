# План разработки сервиса «найди мастера» — единый план

Этот план заменяет собой два прежних документа (`Мы разделим работу на два
независимых бл...md` и `dop_tz.md`). Раньше это были «основной план» +
отдельный «патч» к нему — неудобно читать, непонятно что актуально. Теперь
это один источник правды: шаги идут в порядке приоритета, а статус
(`[x]` / `[~]` / `[ ]`) отражает реальное состояние кода в этом репозитории
на 2026-07-25, а не то, что «должно быть».

Файлы:

## Принятые решения (с обоснованием)

### 1. Города и посёлки-спутники Туркменабада

**Решение: добавить nullable self-reference `parent_city_id` в таблицу `cities`,
без отдельной модели «районов».**

Почему не отдельная модель `District`:
- Запуск идёт в одном городе — полноценная иерархия районов сейчас не нужна,
  это сложность, которую придётся тащить без пользы прямо сейчас (нарушает
  собственный принцип проекта — dop_tz.md справедливо избегает лишних
  абстракций везде).
- `City` уже спроектирована как гибкая справочная таблица
  (`name_ru`/`name_tm`/`is_active`) — этого достаточно и для посёлков.

Почему не «просто отдельные города без связи» (как в исходном плане):
- Посёлки в 15–20 минутах езды — это фактически один рынок труда для
  мастера. Если клиент из Туркменабада ищет сантехника, а мастер числится
  в посёлке Сеятлы, при плоском списке городов клиент его не увидит и
  решит, что мастеров нет вообще. Это прямой удар по наполненности каталога
  на старте, когда мастеров и так мало.

Как это работает:
- `cities.parent_city_id` (nullable, `foreignId('parent_city_id')->nullable()->constrained('cities')`).
- Туркменабад — обычная запись с `parent_city_id = null`.
- Посёлки — отдельные записи с `parent_city_id = <id Туркменабада>`.
- В `MasterController@index`: если передан `city_id` без `parent_city_id`
  (т.е. это «головной» город), в выборку попадают мастера с
  `city_id = X OR city.parent_city_id = X`. Если передан `city_id` посёлка —
  выборка только по нему (клиент из посёлка может явно сузить поиск).
- В `GET /api/cities` посёлки можно возвращать вложенными в родителя или
  плоским списком с полем `parent_city_id` — решает мобильный UI (см. `02-mobile.md`).
- Не ломает то, что уже написано: старые записи (Ашхабад, Мары, Дашогуз,
  Балканабад) просто остаются с `parent_city_id = null`.

### 2. React Native (Expo) vs Vue для мобильного приложения

**Решение: остаться на React Native / Expo — подтверждено.**

Понимаю опасение — Vue тебе роднее. Но смотрю на факты в репозитории:
`ServiceApp/` уже содержит ~10 рабочих экранов (Login, Register, Catalog,
MastersList, MasterDetail, MyProfile, EditProfile, Search, MyQR),
`useAuth`-хук, API-клиент, настроенную навигацию (`@react-navigation`) —
это не черновик, а стек с реальным прогрессом.

Причины не переписывать на Vue-стек (Ionic+Capacitor / NativeScript-Vue):
1. **Потеря сделанного.** Переписывание ~10 экранов + навигации + auth-флоу —
   это недели работы ради смены языка компонентов, без нового продуктового
   результата.
2. **Экраны здесь простые (CRUD + формы + камера + QR).** Сложность именно
   React (сложный state management, эффекты, рендер-циклы) в этом проекте
   почти не участвует. То, что тебе нужно уметь читать/проверять — это
   плоские компоненты с `useState`/`fetch`, а не глубокий React.
3. **Экосистема.** Camera/image-picker, deep links (`expo-linking`, важно для
   QR-сценария из `01-backend.md`/`02-mobile.md`), push-уведомления,
   secure-store — всё это в Expo первоклассное и документированное.
   Ionic+Vue даёт то же через Capacitor-плагины, но рендер идёт в WebView —
   для списков/карточек разницы почти нет, но ощущается на анимациях и
   тормозах загрузки. NativeScript-Vue даёт настоящий нативный рендеринг,
   но community на порядок меньше — сложнее гуглить проблемы и получать
   помощь, в том числе от меня: меньше примеров кода, на которых я обучен.
4. **Твоя роль может быть не «писать JSX руками», а «ревьюить и тестировать
   функционально».** Я пишу React-код, ты проверяешь, что кнопка работает,
   а не гоняешься за версткой. Если тебе всё же понадобится писать самому —
   компоненты в этом проекте однотипны, паттерн быстро схватывается за
   пару экранов.

Подтверждено — план и весь код мобильного приложения продолжаются на RN/Expo.

### 3. SMS-шлюз для Туркменистана

OTP-логика (Этап 2A) уже реализована поверх интерфейса `SmsGateway`, и
поверх него теперь есть две рабочие реализации — `VonageSmsGateway` и
`TwilioSmsGateway` (переключаются через `SMS_GATEWAY` в `.env`, дефолт
по-прежнему `LogSmsGateway`: код пишется в лог, реальные SMS никуда не
уходят). Кабинетная часть спайка проведена — полный разбор в
[`sms-gateway-spike.md`](./sms-gateway-spike.md). Кратко: у Vonage есть
отдельная страница правил для `+993` (P2P запрещён, sender ID
подменяется, двусторонний SMS не поддерживается), у Twilio/Infobip только
общий прайс-лист без деталей, и ни один публичный источник не подтверждает
реальную доставку OTP на живой номер — вопрос **остаётся открытым**, не
«наверное сработает» и не «точно не сработает». Написанный код не решает
этот вопрос сам по себе — он лишь снимает задержку между «провайдер
подтверждён» и «фича включена»: финальный шаг — отправка через
Vonage/Twilio триал на реальный `+993`-номер — нужен человеку (инструкция
в спайк-документе), пройти регистрацию в провайдере или отправить SMS на
номер, которого у меня нет, я не могу.

**Важно: это больше не блокирует запуск MVP.** Ручная модерация мастеров
администратором (Этап C2, уже реализована) работает как самостоятельная
замена верификации телефона — можно запускать, не дожидаясь исхода этого
вопроса, и подключить реальный SMS-провайдер позже, когда найдётся время
на живой тест.
